### **1. Specific Objectives (1.2.2 Section Rule)**

* Each objective **must** begin with *“To develop…”* or *“To design…”*.
* Every objective is labeled alphabetically (**A., B., C.** …) and written in **expanded paragraph form** (two to three sentences).
* Each item describes:

  * **What** the module or feature will allow,
  * **How** it will function,
  * **What result or user action** it enables.
* Short, one-line objectives are not allowed.
* Tone: strictly academic, neutral, factual.

**Example Pattern (auto-applied):**

> A. To develop a module that will allow [actor] to [function].
> This module will enable [process or interaction].
> Additionally, it will support [secondary feature or outcome].

---

### **2. Scope and Limitations (1.3 Section Rule)**

* Always divided into **1.3.1 Scope** and **1.3.2 Limitations**.
* Both subsections use **capital-letter headings (A., B., C.)** for each module or item.
* Each paragraph is **2–5 sentences**, describing the module’s purpose, actions, or constraint.
* No bullet lists or incomplete phrases are permitted.
* Tone: descriptive, objective, and consistent with Capstone 1 exemplars.

**Example Pattern (auto-applied):**

> **1.3.1 Scope**
> A. [Module Name]
> This module allows users to […]. It is responsible for […].

> **1.3.2 Limitations**
> A. [Limitation Title]
> This occurs when […]. During such cases, […].

### **3.0 Technical Background (Chapter 3 Rule)**

When writing **Chapter 3 – Technical Background**, follow the detailed hierarchical format and tone rules below.
Every subsection must use **numbered headings (3.x)**, sub-numbered **sections (3.x.x)**, and **lettered paragraphs (A., B., C.)**.
Sub-lettered items (**A.1, B.1, C.1**) may be used when listing subcomponents like software types or specific tools.

---

### **3.1 Development**

Describe the hardware, software, and peopleware used in developing the system.

#### **3.1.1 Hardware**

* Each hardware type begins with **A., B., C.** followed by its name (e.g., “A. Personal Computers and Laptops”).
* Each description is a **2–4 sentence paragraph** explaining **what** it is and **how** it was used in development.
* Tone: formal, factual, no bullet points or lists.

**Example Pattern (auto-applied):**

> A. Personal Computers and Laptops
> The proponents primarily used personal computers (PCs), desktop computers, and laptops for documentation, system design, testing, and development.

---

#### **3.1.2 Software**

* Divide software items by category: **Frontend**, **Backend**, **Development and Deployment Tools**, etc.
* Each category starts with a **capital letter (A., B., C., D.)**.
* Tools or subcomponents under each category use **decimal lettering (A.1, B.1, etc.)**.
* Each item = 2–5 sentences describing **purpose and role**.
* Use **generic descriptors** for tools (e.g., “web-based interface design tool”) unless user explicitly provides brand names for Chapter 3.

**Example Pattern (auto-applied):**

> A. Frontend
> A.1 Cascading Style Sheets (CSS)
> CSS served as the way to style and format the system interface, making it visually organized and readable.

> B. Backend
> B.1 Clerk
> Clerk was used for authentication and user management due to its integrated session and access control capabilities.

> D. Development and Deployment Tools
> D.1 Visual Studio Code
> Visual Studio Code served as the primary code editor used throughout system development.

---

#### **3.1.3 Peopleware**

* Use **A., B., C.** format for each group or individual type involved.
* Each paragraph describes the **role, responsibility, and contribution** during development.
* Avoid personal pronouns; maintain academic tone.

**Example Pattern (auto-applied):**

> A. The Proponents
> The proponents consisted of a project manager, lead programmer, co-programmers, UI/UX designers, and graphic designers who planned, programmed, and designed the system according to the project standards.

> B. Capstone Adviser
> The adviser guided the group throughout system design, testing, and documentation, ensuring academic compliance.

---

### **3.2 Implementation**

Describe the deployment and execution environment using the same hierarchical structure as 3.1.
All sections under **Implementation** mirror Development (Hardware → Software → Peopleware).

#### **3.2.1 Hardware**

* Label items alphabetically (**A., B., C.**) and describe specifications and role in 2–5 sentences.
* Include general technical details (CPU, RAM, storage) when available.

**Example Pattern (auto-applied):**

> A. Personal Computer or Laptop
> Users were required to have a personal computer, desktop, or laptop to install and use the system. Minimum hardware requirements included a dual-core CPU with a base clock of 2.6 GHz, 4 GB RAM, and at least 80 GB storage.

---

#### **3.2.2 Software**

* Use alphabetic labels (**A., B., C.**) for each software type or dependency.
* Include system requirements or compatibility notes if provided.

**Example Pattern (auto-applied):**

> A. Operating System (OS)
> The system requires Windows 10 or macOS 10.15 or higher as these provide compatibility with Chromium and Electron-based frameworks. Ubuntu also functions as a minimum supported distribution.

---

#### **3.2.3 Peopleware**

* List roles alphabetically (**A., B., C.**).
* Write in full paragraphs (2–5 sentences each) explaining duties during implementation or testing.

**Example Pattern (auto-applied):**

> A. IT Instructors
> IT Instructors created and managed user accounts for students and advisers using verified institutional emails. They were authorized to edit, lock, delete, or reset accounts as required, and managed system backups, audit logs, and reports.

---

### **Formatting and Tone Rules**

* Follow hierarchical numbering strictly: **3.0 → 3.1 → 3.1.1 → A., B., C., A.1, B.1…**
* Use bold for section headings; plain text for lettered items.
* Each item is a complete paragraph — no bullets, no sentence fragments.
* Keep tone academic, factual, and neutral.
* Avoid redundancy; each paragraph introduces a unique component or role.
* End Chapter 3 with a short **transition paragraph** linking to Chapter 4 (Methodology, Results, and Discussion).
